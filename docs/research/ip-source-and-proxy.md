# 调研：反爬 IP 来源与代理方案

- 对应 ticket：wayfinder research #4「调研：反爬 IP 来源与代理方案」（Part of #3）
- 调查日期：2026-10-08
- 调查分支：`research/ip-proxy`
- 结论一句话：**本场景不需要代理 IP 池，各客户端用本机出口 IP 足够**；反爬真正要分配的资源是「浙图账号 cookie + 请求速率预算」，而不是 IP。

---

## 1. 为什么是「账号 + 速率」而不是「IP」

### 1.1 目标站点看不到客户端 IP

爬虫请求的是浙图代理镜像，而非方正源站。实测一次未登录请求的响应头（本仓库内执行）：

```
$ curl -sS -I https://apabi--com.elib.zyproxy.zjlib.cn/zjlib/
HTTP/1.1 302 Found
Server: nginx/1.30.4
Location: https://login.elib.zyproxy.zjlib.cn/index.php?pre=https%3A%2F%2Fapabi.com%2Fzjlib%2F
```

`Location` 的 `pre` 参数把 `apabi--com` 还原成 `apabi.com`，说明这是标准的**URL 重写式反向代理**（浙图的 `zyproxy`/`vpn358`）。链路是：

```
客户端(自家庭宽带 IP) --HTTPS--> 浙图网关 elib.zyproxy.zjlib.cn --(服务端出站, 浙图出口 IP)--> apabi.com
```

方正源站（`apabi.com`）建立连接的来源是浙图网关的出口 IP，客户端 IP 在网关这一跳就被终结。因此：

- 换客户端 IP，对 apabi 侧的风控没有任何作用——apabi 看到的来源始终是浙图的那（几）个出口 IP。
- 换账号，对 apabi 侧同样没有作用——apabi 无法从请求里区分是哪个浙图账号。
- apabi 唯一能施加的压力维度是「从浙图出口 IP 进来的总体速率」，这只能靠整体限速缓解，换 IP 池绕不过去。

> 依据：`apabi_parser.py` 的 `BASE_URL`（本仓库）；浙图网关实测 302 跳转；vpn358 官方文档《访问统计系统简介》明示原理为“访问代理加域名重写技术”（https://doc.vpn358.com/introduce）。

### 1.2 浙图侧的管控维度是「读者账号」

vpn358（浙图代理所用系统）官方介绍里，明确的能力都在账号维度：

- “详细记录读者账号、下载论文篇名，统计了论文总下载篇数，而且与汇文系统深度整合，获取读者账号信息”；
- “下载监控功能……各个图书馆可以根据实际情况，**限制读者可以使用的流量和论文下载篇数**”；
- “高级访问限制：不但可以限制读者访问的流量，还可以限制读者下载论文的篇数”；
- “**无并发限制**：与传统 vpn 不同，vpn358 授权访问系统不限制用户并发数”；
- 容量参考：“普通 PC 电脑，2G 内存，可以支持每天一万篇的下载量……每天……2 万篇论文时，无需任何的负载均衡”。

即：代理软件本身不限并发，图书馆可以按账号设流量/篇数上限，并留有逐账号下载日志。这是本场景里最真实、最可能触发的“反爬/风控”。图书馆的通用服务条款也把处置落在账号上（“停止为违规账号提供 VPN 服务”、禁止“网络下载工具进行恶意批量下载”、禁止账号转借），例如贵州大学图书馆远程访问条款（https://lib.gzu.edu.cn/2010/1207/c16793a245263/page.htm）。

**推论（标注为推断）**：既然 apabi 只看到网关出口 IP、浙图按账号计量，那么“反爬 IP 池”在本场景打不到任何一个真实的控制点。换 IP 只改变网关看到的来源，不改账号暴露面，也不改 apabi 侧。

## 2. 日志与现有限速策略：站点限流强度线索

### 2.1 分析方法

统计 `logs/crawl.log*` 全部 14 个文件的 WARNING/ERROR 行，按错误签名归类；提取所有出现的 HTTP 状态码与失败主机。脚本要点（可复现）：

```python
# 逐行匹配 "YYYY-MM-DD HH:MM:SS,mmm LEVEL logger: msg"
# 归两类: (1) msg 内 "HTTP <code>" -> 状态码; (2) "信号灯超时"/"Cannot connect" -> 连接层失败
# 并统计失败 URL 的主机、按天/按分钟聚合突发
```

覆盖范围：2026-08-02 ~ 2026-09-12，共 565,411 行（INFO 516,190 / WARNING 42,832 / ERROR 2,462）。

### 2.2 结果

| 签名 | 次数 | 说明 |
|---|---:|---|
| `CONNECT_SEMAPHORE_TIMEOUT`（`Cannot connect to host …:443 … [信号灯超时时间已到]`） | **29,999** | TCP 连接层失败，Windows 套接字信号灯超时（WSA 121），**全部指向网关主机** `apabi--com.elib.zyproxy.zjlib.cn` |
| `AUTH_FAIL`（重定向到登录域/含登录页特征） | 2,458 | cookie 会话失效，账号维度 |
| `HTTP_4xx_5xx` | 2,407 | **只有 `502` 一种状态码**，无 403/429/503 |
| 其余（重试耗尽兜底、`_ProactorBasePipeTransport` 回调、无文章等） | ~30 | 零散 |

关键观察：

1. **没有任何 `429`（也没有 `403`）**。站点并未以应用层“按来源 IP 限流”的方式回击，代理池要绕的那种限流信号在本数据集里不存在。
2. **唯一的 HTTP 错误是 `502`**，来自网关（`nginx/1.30.4`）。502 的语义是反向代理从上游拿到无效响应/上游超时——压力信号在网关↔源站之间，而不在客户端↔网关之间。
3. **连接层失败全部发生在同一个网关主机**，且呈突发而非均匀分布：2026-08-08 一天 26,625 次（自 19:54 起，分钟峰值 256），2026-09-11 1,706 次，2026-09-12 188 次。这更像网关/链路容量事件，而不是逐 IP 的稳定配额。
4. 代码内已记录一条服务端 throttle 现象：图片 CDN 在“持续高压”下从 ~1s 退化到 20s+（`apabi_http.py` 注释）。这也是服务端在**整体吞吐**维度的降级信号。

### 2.3 现有限速策略评估（`crawler/adapters/apabi_http.py`、`config.py`）

- HTML：并发信号量 8，每请求前 `random.uniform(0.3, 1.0)`s，3 次重试指数退避（1/2/4s），总超时 30s。
- 图片：独立低并发信号量 6，短超时 15s，不叠加随机延迟（靠并发数保护 CDN）。

评估：这套策略针对的是“别把网关/上游打爆”，方向正确。日志里的 `502` 与连接超时正是“总体压力超过网关承载”的表现，说明**继续收紧的是全局速率/并发，而不是换 IP**。若未来上多客户端，风险是多台叠加后把全局速率抬回高位，重新触发这批 502/超时——所以中心必须做**全局速率预算**（见 §4），不能让每台各自跑满 `concurrency=8`。

## 3. IP 来源方案对比

前提：客户端 2~5 台自备机器，各自家宽出口 IP 互不相同；账号池多个浙图账号；目标经浙图网关代理到 apabi。

| 方案 | 成本（2026 市场参考） | 对 apabi 风控效果 | 对浙图侧效果 | 运维/合规 | 结论 |
|---|---|---|---|---|---|
| **客户端本机出口（现状）** | 0 | 无（被网关 IP 掩盖） | 若浙图按来源 IP 限流则天然分散；据 §2 未见此类限流 | 无额外运维 | **足够** |
| 国内动态/隧道代理 | 动态短效 5~20 元/万 IP；隧道 100~600 元/月；住宅静态 30~100 元/IP/月 | 无 | 可分散来源 IP，但收益未证实 | 需接入、轮换、可用性验证；机房 IP 段反而更易被识别 | 不需要 |
| 海外住宅代理 | \$0.49~\$8.00/GB | 无 | 海外来源 IP 访问国内图书馆代理，易触发异地/异常登录 | 高，且延迟上升 | 不需要 |
| 云出口（阿里云 EIP/NAT/轻量 ECS） | EIP 保有费 ~0.02 元/小时/个 + 流量/带宽；NAT 实例 0.115~0.23 元/小时 + CU 0.184 元/GB | 无（机房 IP） | 来源收敛为少数固定机房 IP，可能更显眼 | 中高，需运维与备案 | 不需要 |
| Cloudflare Workers 出口 | 免费额度内 | 无；Workers 默认共享出口 IP，无固定出口（专用出口 IP 属 Enterprise 产品） | 不适用 | 高 | 不适用 |

成本来源（公开报价，2026）：

- 国内：悟空代理/快代理/有代理等国内厂商价格汇总页（动态 5~20 元/万 IP、隧道 100~600 元/月、住宅静态 30~100 元/IP/月）；快代理定价页隧道代理约 ¥506.12/月起（https://www.kuaidaili.com/pricing/）。
- 海外住宅代理：2026-10-06 市场快照，\$0.49/GB（Evomi）到 \$8.00/GB（Bright Data PAYG，促销 \$4）（https://marketintelligencetools.com/reports/proxy-pricing/）。
- 阿里云：EIP 按量付费公网 IP 地址单价 0.02 元/小时/个（中国大陆，https://help.aliyun.com/zh/eip/pay-as-you-go/）；NAT 网关实例费单可用区 0.115 元/小时、CU 单价 0.184 元/个/小时（https://help.aliyun.com/zh/nat-gateway/nat-gateway-billing）。
- Cloudflare：Workers 无静态出口 IP，Dedicated egress IPs 为独立产品（https://developers.cloudflare.com/smart-shield/configuration/dedicated-egress-ips/other-products/）。

> 附注：上表把“对 apabi 风控效果”统一记为“无”，依据是 §1.1 的链路事实（apabi 只看到浙图出口 IP）。这不是经验断言，而是架构决定的。

## 4. 建议（给调度中心的设计）

1. **中心不分配 IP，客户端用本机出口。** 多台机器不同家宽 IP 已经天然分散，且对 §2 观察到的网关瓶颈无额外帮助也无害。
2. **中心分配的是「账号 cookie」与「速率预算」**：每个客户端领到的不是 IP，而是一组账号 cookie + 一个全局令牌桶配额。中心维护**全局**请求速率/并发上限，按客户端下发；任一时刻全局合计不超过单机现在的量级（参考 `concurrency=8`、0.3~1.0s/请求），避免叠加后重演 502/连接超时。
3. **账号独占分配**：一个 `vpn358_sid` 同一时刻只借给一个客户端，避免同一会话多机并发在浙图侧形成异常。账号维度才是会被“封/停”的资源（§1.2、§2.2 的 `AUTH_FAIL`）。
4. **告警按维度分开**：`AuthError` 走账号维度告警与补录（对应 cookie 池 ticket #8）；`502`/连接超时走网关维度，处置是**降速**而非换 IP。
5. **要提吞吐，先加客户端机器。** 复用现有账号与家宽，边际成本为 0，且不引入新的合规风险；代理池放最后，且只在有可观测证据时才考虑。
6. **保留礼貌限速与随机延迟。** 现有 0.3~1.0s 随机延迟是对付网关/上游整体压力的正确手段；换 IP 不能替代它。

### 触发重新评估的条件（可观测信号）

出现下列任一证据，才值得回头考虑 IP 来源方案：

- 单个客户端**本机出口 IP** 被网关单独针对（同一有效 cookie 下，仅该 IP 持续返回 302 到登录页 / 连接被拒），而其它 IP 正常；
- 日志出现 `429` 或明确的按来源 IP 限流响应，而非现在的 `502`/连接超时；
- 网关在“单机、低速率”下也稳定 `502`，且与来源 IP 相关。

当前数据（§2）不支持上述任一情形。

## 5. 未决与风险

- **合规**：图书馆条款禁止账号转借与下载工具批量下载，违规的直接后果是停账号。代理池换 IP 不降低账号暴露面，反而可能因来源 IP 异常（异地/机房）增加被风控概率。本调研只评估工程可行性，不改变合规约束。
- **apabi 是否接收 `X-Forwarded-For`**：本次无法在未认证状态下验证网关是否把客户端 IP 透传给上游。若透传，apabi 侧仍可能区分客户端——但这与“换 IP 即安全”的假设方向相反（透传意味着 apabi 本来就能看到，换池也无意义）。列为待验证项，需一次带 cookie 的抓包确认。
- 日志仅覆盖单机运行期（2026-08~2026-09），多客户端叠加后的网关行为属外推。
